# 知行数据安全、升级与备份契约

状态：设计基线，P0 缺口未闭环（2026-08-14）

目标不是承诺任何故障都不丢数据，而是保证覆盖升级不静默清空、迁移失败可恢复、远端备份可验证。

## 不可破坏的原则

1. 正常覆盖安装不得清空或静默重建用户数据。
2. 禁止 destructive migration；迁移失败必须保留原始数据并进入可恢复状态。
3. 用户原文与可重建 RootFS、缓存、索引分开存放。
4. 备份只有在“生成、上传、远端读回、完整性校验”全部通过后才算成功。
5. 任何恢复都先写 staging、校验完成后原子替换，失败不得破坏当前数据。
6. application ID、正式签名、数据库逻辑名称和单调递增的 `versionCode` 是稳定升级身份。

## 当前事实与缺口

当前代码证据：

- application ID 为 `dev.sundby.zhixing`，Room 数据库逻辑名为 `zhixing`，schema 版本为 50。
- Room 存在连续迁移注册，未启用 destructive fallback。
- v49→v50 仅新增持久子智能体运行记录和请求唯一索引，不改动既有数据。
- v48→v49 只新增结构化健康记录表及索引；不回填或复制 Lenovo Watch 最近快照，并保留全部既有用户数据。
- v47→v48 只为 Work 会话增加可空 `active_turn_id`；v46→v47 只增加默认关闭的 `fast_mode`。两次迁移
  都保留既有聊天、记忆、Work 会话、Agenda、长期计划、知识库和用户文件；0.4.13→0.4.14 schema 保持 48。
- v45→v46 按明确的产品清理边界删除旧 `assistant_tasks`、`assistant_task_events` 和
  `assistant_task_links`。这些记录只用于普通聊天任务的运行追踪和 Today 投影，不是聊天、记忆、Agenda 或
  外部写入结果的事实来源；迁移保留这些用户语义数据以及 `assistant_runtime_contexts`，并有 45→46 设备迁移
  测试验证该边界。
- v44→v45 为对话增加用户提示词快照列；已有对话不会在升级后静默采用知识库提示词。
- v43→v44 新增记忆文档表，将旧记忆保留到 legacy archive，升级本身不删除旧表或会话。归档后续只允许
  维护既有文件；用户删除 legacy 条目或整档时，归档 CAS 与对应旧 `MemoryEntity` 的物理删除位于同一
  Room 事务，防止界面已删除但旧表仍留隐藏副本。
- v42→v43 纯新增普通聊天任务、事件、软链接与隐藏运行时上下文表且零回填；v41→v42 只给待办增加
  可空重复频率与默认间隔；v40→v41 只新增月度收支与渠道汇总表及索引；
  v39→v40 扩展 Work 运行时身份，这些迁移均保留
  既有会话、事项、长期计划与其他用户数据。
- Workspace 用户文件位于 `files/workspaces/<root>/files`，OrbitOS 知识库位于其中的 `vault/`，
  二者都与可替换的 `linux` RootFS 分离。
- WebDAV、S3、手动导入导出和备份提醒已有基础实现。
- WebDAV/S3 新建数据库备份使用 `zhixing.db`、`zhixing-wal`、`zhixing-shm`；恢复优先识别该命名，
  同时将旧备份中的 `rikka_hub.db`、`rikka_hub-wal`、`rikka_hub-shm` 映射回当前逻辑库。
- 数据库恢复先解压到 cache staging，以应用同一套 Room、迁移链和 SQLite 扩展真实打开并校验 schema，
  再执行 SQLite `quick_check`，关闭活库 Room 后替换主库；替换前保留
  rollback 副本，缺失的 WAL/SHM 会清除旧 sidecar，安装失败时尝试恢复原库。Room 一旦关闭，无论安装
  成功或失败，界面都会要求立即重启应用。

P0 缺口：

| 缺口 | 风险 |
| --- | --- |
| FILES 备份未覆盖 `files/workspaces/` | Workspace 与知识原文可能遗漏 |
| 定时备份只是提醒，没有后台备份 Worker | 用户以为有自动保护但实际未执行 |
| 同步凭据尚未完成 Keystore 边界 | Secret 保护不足 |
| 缺少可重复执行的公开版本种子到当前版本自动化升级测试 | 每次发布仍依赖候选包与正式签名包的覆盖升级验收，无法持续回归全部数据不变量 |
| 备份缺少统一 manifest、哈希、读回校验和恢复演练 | 无法证明备份真的可恢复 |
| Settings、FILES 与数据库尚未形成统一 staging/回滚事务，FILES 路径校验未统一 | 整包恢复中途失败仍可能产生部分恢复 |
| 数据库主库/WAL/SHM 仍是进程内多文件替换，启动时未自动接管中断遗留的 rollback 目录 | 替换窗口内进程退出仍需恢复机制 |

以上缺口闭环前，不得把现有 WebDAV/S3 描述为完整灾难恢复。

## 数据分类

| 数据 | 事实来源 | 升级 | 远端备份 |
| --- | --- | --- | --- |
| 会话、消息、记忆、待办、月度收支汇总、结构化健康记录、工作区元数据 | Room `zhixing` | 必须保留 | 必须 |
| Provider、助手、外观、同步配置 | DataStore | 必须保留 | 必须 |
| 普通上传附件、Skills、Workspace 用户文件与 `vault/` 原文 | 应用 `files/` | 必须保留 | 必须 |
| 普通聊天任务追踪、事件与软链接 | Room `zhixing` 的可重建投影 | 可按明确迁移与生命周期契约清理 | 非恢复真值 |
| 成功保存月度汇总后的账单附件与对应 OCR 缓存 | 临时输入 | 按月度汇总契约清理 | 不作为持久备份对象 |
| Workspace RootFS、派生索引、缓存和临时工具输出 | 可重建数据 | 可重建 | 默认不备份 |

知识原文必须位于持久 `/workspace/vault`，不得只存放在 RootFS 的 `/root`、`/var` 或 `/tmp`。
助手的知识库用户提示词属于该 vault 原文；当前对话使用的提示词快照另存于 Room，因此 vault 文件后续修改、
缺失或未被 FILES 备份不会改变已有对话，但会影响新对话是否回退到应用配置。跨设备保留最新提示词仍依赖
用户的 vault Git/Workspace 备份，不能把 Room 快照当成 vault 文件备份。

月度账单上传是一个明确例外：当同一来源批次关联的月度汇总保存全部成功且来源消息脱敏已落库后，
应用会从来源消息移除附件引用，并尝试删除位于受管上传目录中的原附件与对应 OCR 缓存。物理文件仍被
其他消息、分支、媒体类型或工具结果引用时不会删除；底层存储失败时也可能留下没有来源消息引用的本地
残留。备份流程不应把这类已完成导入的临时输入恢复为长期附件；如果备份在清理前已经生成，其中的旧
副本不会被清理动作追溯删除。原材料已经发送给远端模型时，本地删除也不能撤回远端已经接收的数据，
远端保留期限仍受所选 Provider 的数据政策约束。

## 升级契约

公开版本升级应遵循：

1. 首次打开新 schema 前，快照数据库/WAL/SHM、Settings 和用户文件清单。
2. 为快照生成 manifest 与 SHA-256，验证后原子写入版本化 recovery 目录。
3. Room 与文件迁移在事务或 `source -> staging -> validate -> atomic rename` 边界内执行。
4. 迁移完成后校验关键表、对象数量、外键/索引和用户文件哈希。
5. 失败时允许导出旧快照、重试或恢复，不自动执行破坏性重建。

迁移测试至少覆盖“前一公开版本 -> 当前版本”，长期保留首个公开稳定版到当前版本的种子升级路径。
有意删除或重建用户语义数据时，必须由产品契约明确记录并用迁移测试证明影响边界。

## 备份与恢复契约

备份包必须有版本化 `manifest.json`，每个条目记录规范化相对路径、大小和 SHA-256。路径不得包含绝对
路径、`..`、空字节或逃逸目标目录的符号链接。

- 模型 API Key、WebDAV 密码、S3 Secret 和明文恢复密钥不得进入普通备份。
- 备份生成后本地重开校验，上传后读回 manifest/元数据校验。
- 新失败备份不得覆盖最后一个已验证成功备份。
- 远端备份采用带认证加密；Keystore 只保护本机材料，不能成为跨设备恢复的唯一密钥。
- 恢复必须拒绝损坏 manifest、错误密钥、哈希不符和路径逃逸。

首版先保证完整恢复，再做增量和保留策略。默认建议保留 3 份本地升级快照、7 份每日和 4 份每周远端
备份；删除旧备份前必须确认存在更近且已验证成功的恢复点。

## 自动备份

使用唯一 WorkManager 周期任务和同一个 BackupCoordinator：

- 用户明确配置并启用后运行，可选网络、Wi-Fi、充电和电量约束；
- 周期、主动“立即备份”和导入大量资料后的事件触发复用同一执行链；
- 失败指数退避；认证或密钥问题进入 `NEEDS_USER_ACTION`；
- 成功默认静默，设置页分别显示最后尝试与最后成功时间；
- 大型 Workspace 超出普通后台预算时使用有通知的前台任务。

## 发布门禁与实施顺序

稳定 Release 至少验证：

- [ ] 用公开版本种子数据覆盖安装候选 APK；
- [ ] Room 与文件迁移后，对象数量、关键字段和文件哈希符合预期；
- [ ] 本地备份与恢复 round-trip 成功；
- [ ] 损坏包、错误密钥、路径逃逸和中断上传不破坏现有数据。

实施顺序：

1. **P0：修正事实错误。** 覆盖 Workspace 文件、保护同步凭据，并统一 Settings、FILES 与数据库的
   staging、路径校验、整包提交和失败回滚。
2. **P1：可恢复升级。** 增加升级前快照、manifest、校验、恢复模式和设备升级测试。
3. **P2：自动加密备份。** 增加 BackupCoordinator、Worker、读回校验、恢复码和恢复演练。

## 非目标

- 不承诺卸载应用或清除系统数据后仍能从本机恢复。
- 不备份用户未授权的外部目录或可重建数据。
- 不用 PRoot `cron` 替代 Android WorkManager/前台任务。
- 首版不做多人协作、实时双向同步或跨设备冲突合并。
