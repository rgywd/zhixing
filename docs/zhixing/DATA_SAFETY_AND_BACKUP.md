# 知行数据安全、升级与备份设计

状态：设计基线，P0 待实施（2026-07-16）

本文定义知行从首个公开版本 `v0.1.0` 开始必须遵守的数据安全契约。目标不是承诺任何故障下都绝不丢失，而是让正常覆盖升级可验证、迁移失败可恢复、误删或设备损坏有独立备份可还原。

## 1. 安全目标

- 正常覆盖安装不得清空或静默重建用户数据。
- 数据结构升级失败时保留升级前原始数据，并进入可恢复状态。
- 应用内误删、手机丢失、存储损坏和卸载重装由独立远端备份兜底。
- 备份成功必须以“生成、上传、远端读回、完整性校验”全部通过为准。
- 知识库、工作区和未来新增的持久化对象必须进入同一套分类、迁移、备份和恢复契约。
- RootFS、缓存和索引等可重建数据不得与用户原始内容混为一体。

## 2. 当前实现与已知缺口

当前已经具备：

- 正式包名为 `dev.sundby.zhixing`，`v0.1.0` 已使用知行长期发布签名。
- Room 数据库当前版本为 35，已声明从 1 到 35 的连续自动或手工迁移链。v33 迁移已删除旧
  Work/Happy/App Server/Codex catalog 表并建立 Phone-line 表；v34–v35 继续按显式迁移链演进。
- Room 未启用 destructive migration；迁移缺失时应失败，而不是主动删库。
- Workspace 用户文件位于应用内部 `files/workspaces/<root>/files`，与可替换的 RootFS `linux` 目录分离。
- WorkManager 与 Koin WorkManager 工厂已接入。
- WebDAV、S3、手动导出和恢复已有基础实现。

P0 缺口：

1. Room 实际数据库名为 `zhixing`，WebDAV/S3 备份与恢复仍读取旧名称 `rikka_hub`。
2. 现有 FILES 备份覆盖上传文件、Skills 和字体，但不覆盖 `files/workspaces/`。
3. 当前“定时备份”只是到期提醒，没有后台 Worker 自动执行备份。
4. WebDAV 密码和 S3 Secret 随 Settings 配置存储，尚未建立 Android Keystore 保护边界。
5. 迁移测试主要覆盖 `11 -> 12`，尚无从公开版本数据库到当前版本的完整升级验证。
6. 备份文件缺少统一版本化 manifest、逐项 SHA-256、远端读回校验和恢复演练。

在这些缺口修复前，不得把现有 WebDAV/S3 功能描述为完整灾难恢复方案。

## 3. 不可变升级身份

从 `v0.1.0` 起冻结以下身份：

- application ID：`dev.sundby.zhixing`
- 发布签名证书 SHA-256：`FE:57:58:35:13:D2:8D:23:7F:FD:7C:E7:9D:FA:D3:10:74:D5:8C:1B:E5:CE:E1:49:AA:C0:0C:F5:CC:7A:AE:9C`
- 数据库逻辑名称：`zhixing`
- 正式版本的 `versionCode` 必须单调递增。

更换 application ID 会被 Android 视为新应用；更换签名会被 Android 拒绝覆盖安装。这两项不得作为普通重构内容修改。数据库文件名和持久化目录如需调整，必须提供显式兼容迁移，不得直接改常量后让旧数据失联。

## 4. 数据分类与事实来源

| 数据 | 事实来源 | 升级保留 | 远端备份 | 恢复方式 |
| --- | --- | --- | --- | --- |
| 会话、消息、记忆、收藏、工作区元数据 | Room `zhixing` | 必须 | 必须 | 数据库迁移或快照恢复 |
| Provider、助手、外观、同步配置 | DataStore | 必须 | 必须 | 版本化 Settings 导入 |
| 上传附件 | `files/upload` | 必须 | 必须 | 文件级恢复 |
| Skills | `files/skills` | 必须 | 必须 | 文件级恢复 |
| Workspace 用户文件与知识库原文 | `files/workspaces/*/files` | 必须 | 必须 | 文件级恢复 |
| Workspace RootFS | `files/workspaces/*/linux` | 可重建 | 不备份 | 重新下载安装 |
| 知识全文/向量索引 | Workspace 隐藏索引目录 | 可重建 | 默认不备份 | 从原文重建 |
| 临时文件、工具输出和缓存 | cache/tmp/tool_outputs | 可丢弃 | 不备份 | 自动重建或清理 |

知识库的原始资料必须写入 `/workspace` 所映射的用户文件区，禁止把唯一副本写入 RootFS 的 `/root`、`/var` 或 `/tmp`。

## 5. 覆盖升级与迁移契约

### 5.1 升级前本地快照

新版本第一次打开数据库之前执行：

1. 读取旧数据库 `PRAGMA user_version` 和旧应用数据版本。
2. 将数据库、WAL、SHM、Settings 和 Workspace 用户文件清单复制到版本化 staging 目录。
3. 生成 manifest 与 SHA-256；验证快照文件可读且不为空。
4. 将 staging 原子重命名为 `files/recovery/pre-upgrade-<version>-<timestamp>`。
5. 快照验证成功后才允许 Room 和文件结构迁移。

本地默认保留最近 3 个成功的升级前快照。删除旧快照只能发生在新版本完成启动、核心数据校验成功并生成新的可恢复点之后。

### 5.2 数据库迁移

- 禁止 `fallbackToDestructiveMigration` 及任何等价的静默删库策略。
- 每个 schema 变更都必须提供 Room migration 或 AutoMigrationSpec。
- 涉及复制、重写或删除列的迁移必须在事务中完成。
- 迁移异常时不得捕获后继续使用部分迁移数据。
- 公开版本升级测试至少覆盖“最近一个公开版本 -> 当前版本”；长期保留 `v0.1.0 -> 当前版本` 的种子数据库测试。
- 迁移完成后验证关键表存在、外键/索引有效、会话/消息/记忆数量不小于迁移前基线。

### 5.3 Workspace 与知识库迁移

- 用户原文和机器生成索引分目录保存。
- 文件格式增加独立 `dataSchemaVersion`，不复用 App `versionName`。
- 迁移采用 `source -> staging -> validate -> atomic rename`，禁止对唯一原件做不可逆的原地重写。
- 派生索引迁移失败时删除并重建索引，不影响原文。
- RootFS 更新只能替换 `linux`，不得删除相邻的 `files`。

### 5.4 失败与恢复

迁移失败时：

- 应用进入恢复模式，不自动重试破坏性操作。
- 展示错误 ID、源数据版本、目标版本和快照位置，不展示密钥。
- 允许导出升级前快照、重试迁移或恢复最近快照。
- 恢复操作先写入 staging 并校验，最后原子替换；失败时保留当前数据和恢复源。

## 6. 备份包契约

备份包必须包含根级 `manifest.json`。建议首版结构：

```json
{
  "formatVersion": 1,
  "appId": "dev.sundby.zhixing",
  "appVersion": "0.2.0",
  "versionCode": 2,
  "databaseVersion": 24,
  "createdAt": "2026-07-16T12:00:00Z",
  "deviceId": "local-random-id",
  "encryption": "AES-256-GCM",
  "entries": [
    {
      "path": "database/zhixing.db",
      "size": 123456,
      "sha256": "..."
    }
  ]
}
```

契约规则：

- `formatVersion` 决定恢复器如何解释包内容。
- 每个条目必须记录规范化相对路径、大小和 SHA-256。
- 路径不得包含绝对路径、`..`、空字节或逃逸目标目录的符号链接。
- 备份不得包含模型 API key、WebDAV 密码、S3 Secret、日志中的请求正文或明文恢复密钥，除非对应字段经过独立加密且用户明确选择。
- 备份生成后必须在本地重新打开并校验 manifest，再执行上传。
- 远端上传后必须读回 manifest 或对象元数据并校验；只有此时才能记录成功时间。
- 新失败备份不得覆盖或删除最后一个已验证成功备份。

## 7. 加密与凭据

- 远端备份默认使用 AES-256-GCM 等带认证的加密格式，不使用只有压缩没有认证的普通 ZIP 作为最终安全边界。
- 跨设备恢复密钥由用户口令通过抗暴力破解的 KDF 派生，并提供可离线保存的恢复码。
- Android Keystore 只用于保护本机缓存的解密材料和 WebDAV/S3 凭据；不能成为跨设备恢复的唯一密钥来源。
- 用户遗失恢复口令时，应用不得声称可以解密端到端加密备份。
- UI 不回显完整 Secret；诊断日志只记录凭据 ID 或脱敏末尾。

## 8. 手机定时备份

### 8.1 调度

使用唯一的 WorkManager 周期任务，用户修改设置时更新同一任务，不创建重复任务。

默认建议：

- 远端自动备份由用户配置目标并明确启用后运行。
- 周期：每日一次；允许选择 1、3、7 天。
- 约束：网络可用、电量不低；用户可选仅 Wi-Fi、仅充电时。
- WorkManager 只保证执行窗口，不承诺精确时刻。
- 失败采用指数退避；认证失败、密钥缺失等不可重试错误进入 `NEEDS_USER_ACTION`。
- 大型 Workspace 备份超过普通后台时间预算时，转为有通知的前台任务。

### 8.2 事件触发

除周期任务外增加：

- 安装更新前：最近一次已验证备份超过 24 小时时，优先生成安全备份。
- 用户导入大批知识资料后：在文件稳定且设备空闲时排队一次增量备份。
- 用户主动点击“立即备份”：复用同一个 BackupCoordinator，不走另一套逻辑。

### 8.3 状态与通知

统一状态：`IDLE`、`RUNNING`、`SUCCESS`、`RETRYABLE_FAILURE`、`FAILED`、`NEEDS_USER_ACTION`。

- 成功默认静默，只更新“最后成功时间、目标、大小、校验状态”。
- 连续重试失败或需要重新登录时发送通知。
- 设置页同时展示最后尝试时间和最后成功时间，禁止用一次失败尝试覆盖成功记录。

## 9. 保留与增量策略

首版优先保证恢复正确，再优化容量：

- 本地升级快照：最近 3 份。
- 远端默认：7 个每日、4 个每周；月度保留由用户开启。
- 删除前确认至少存在一个更近且已验证成功的备份。
- 大型知识库后续改为内容哈希去重或对象级增量备份；manifest 仍代表一个完整可恢复视图。
- RootFS、缓存和可重建索引不进入增量对象集合。

## 10. 发布验证门

从下一版开始，Release 工作流增加数据安全门：

1. 使用公开版本 APK/种子数据创建会话、记忆、Settings、附件和 Workspace 文件。
2. 覆盖安装候选 APK。
3. 启动并完成 Room 与文件迁移。
4. 校验对象数量、关键字段和文件 SHA-256。
5. 执行一次本地备份与恢复 round-trip。
6. 校验恶意路径、损坏 manifest、错误密钥和中断上传不会破坏现有数据。

任一步失败都禁止发布。不能运行设备升级测试时，版本只能标记为内部预览，不得作为稳定更新推送。

## 11. 实施顺序与验收

### P0：修复事实错误

- 统一数据库名称常量为 `zhixing`，WebDAV/S3 兼容读取旧 `rikka_hub` 备份。
- FILES 备份加入 Workspace 用户文件，显式排除 RootFS、tmp 和派生索引。
- 将同步凭据迁移到 Android Keystore 保护的存储边界。

### P1：可恢复升级

- 增加升级前快照、manifest、哈希验证和恢复模式。
- 增加从 `v0.1.0` 到候选版本的设备升级测试。

### P2：自动与加密备份

- 增加 BackupCoordinator、周期 Worker、事件触发和保留策略。
- 增加带认证加密、恢复码、远端读回校验和恢复 round-trip 测试。

完成标准：

- 正常升级后所有种子对象与文件哈希一致。
- 故意令迁移失败时，升级前快照仍可导出和恢复。
- 定时备份在约束满足时运行；失败可重试，认证问题可见。
- 损坏、截断或使用错误密钥的备份无法进入恢复替换阶段。
- 恢复完成后数据库、Settings、附件、Skills 和 Workspace 原文一致；RootFS 与索引可重建。

## 12. 非目标

- 不承诺卸载应用或清除系统数据后仍能从本机恢复。
- 不备份用户未明确授权的外部目录。
- 不通过常驻 PRoot `cron` 保证调度；Android 后台执行由 WorkManager/前台任务管理。
- 不在首版实现多人协作、实时双向同步或跨设备冲突合并。
- 不把派生索引当作知识库唯一副本。
